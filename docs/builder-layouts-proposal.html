How it is built

The rule is that a layout owns arrangement and nothing else. No layout may hold a rule about magnetics, a call to the engine, or a copy of a panel — if a layout needs something a component does not expose, the component grows a prop and every layout gets it.

PieceWhat it isWhy
layouts/index.jskey → component registry, one entry per layout The builder renders <component :is>. Adding a layout is one file plus one line.
BuilderLayoutPropsthe prop set every layout takes, unchanged from today Layouts are interchangeable, so the same battery of tests runs against all of them.
PanelFrame.vuecard chrome: header, title, actions slot The header markup is copied three times today. Extract once, then every layout and both new panels use it.
AlternativesPanel.vuethe third cell of band B and the body of D Wraps ScatterChartComparator. Its rows come from a slot, so the site fills it with the cross-referencer and the embedded builder falls back to the core adviser.
VisualizerSwitch.vue2D / 3D dropdown over the two existing visualizers The choice is asked for in three of the five layouts.
graphRegistry.jsthe graph map lifted out of GraphInfo Lets a band show the wire subset without a second copy of the list. GraphInfo consumes the same map.
density prop on the info cardschanges grid-template-columns only The info cards are already CSS grids; a horizontal band needs three columns instead of one. No markup fork.

Why the alternatives panel needs a slot

Cross-referencing lives in libCrossReferencers.wasm, which the site ships and the embedded builder does not — putting it inside MagneticBuilder would add about 24 MB to every embedder. So the panel declares what it needs and the host supplies it: on openmagnetics.com it is the real cross-referencer, embedded it is the core adviser asked for several candidates instead of one, which costs nothing because it is the same call.

Where the switch lives

Settings, next to the other builder toggles, as a dropdown of the five names. It is a key in magneticBuilderSettings, and that store is already in the profile's roaming whitelist, so the layout follows the account to another computer the same way the unit system does. A printed-winding design offers the planar layout on first open; the choice is remembered and never forced.

Tests

  • One contract battery, run against every layout. Set the layout, then advise a core, change shape and material, advise a wire, and assert the design in the store changed and the console stayed clean. Each layout must satisfy it, which is what stops a layout from quietly dropping a control.
  • Per-layout placement tests only for what is unique: the alternatives chart appears and clicking a point loads that core; the 2D/3D dropdown swaps the canvas; the planar layout renders one row per copper layer and the turn count matches the coil.
  • A switching test: change the layout in Settings with a design loaded, and the design is untouched — layouts arrange, they do not edit.
  • Persistence: the choice survives a reload and travels with the profile, the same check the unit system has.

Order I would build them

  • First the registry, PanelFrame, the density prop and the contract battery, with only layout A registered. Nothing changes on screen; the seam is in place and proven by tests.
  • Then B, which is the one you asked for and the one that needs the two new panels.
  • Then E, because the planar path has the most to gain and the least overlap with the others.
  • Last C and D, which are arrangements of what B already built.
